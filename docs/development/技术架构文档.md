# EasyCV 技术架构文档

## 🏗️ 整体架构

EasyCV 当前采用 Chrome Extension Manifest V3 架构，核心由 `background`、`content`、`popup`、`options` 和 `utils` 五组模块组成。

当前运行时结构与开发入口如下；完整文档归类见[文档索引](../README.md)。

```text
EasyCV/
├── manifest.json
├── _locales/
│   ├── zh_CN/messages.json
│   ├── zh_TW/messages.json
│   ├── ja/messages.json
│   └── en/messages.json
├── background/
│   ├── service-worker.js            # StateManager + BackgroundManager（消息路由/状态缓存）
│   ├── auto-enable-manager.js       # 域名级自动启用（通配符匹配、缓存与防抖）
│   ├── icon-manager.js              # 图标四态、徽章与 tooltip（i18n 模板）
│   ├── monitoring-manager.js        # 状态日志、性能指标、健康检查
│   └── state-confirmation-manager.js# 带 requestId 的状态更新确认/重试
├── content/
│   ├── content.js                   # CopyPasteManager（isolated world）：DOM 处理、SPA 感知
│   └── injector.js                  # main world：原型重写、Shadow DOM 穿透、动态保护
├── popup/

│   └── storage-utils.js
├── scripts/                         # 构建/打包/发布/文档校验/lint
├── test/
```

> 说明：本文档只描述当前仓库中真实存在的文件和由这些文件承载的职责边界，不再把未落地的拆分文件当作现状模块。

## 1.1.2 权限与注入边界

manifest 仅声明 `storage`、`contextMenus`；`host_permissions`、静态 Content Script 的 matches 及 web-accessible resources 的 matches 保留 `<all_urls>`。Content Script 在 `document_start`、所有匹配 frame 中运行；`injectCustomScript()` 通过 `runtime.getURL` 创建扩展内 `content/injector.js` 的 DOM script 标签，未使用 scripting API。普通网页 URL 由现有 host permissions 覆盖，故移除冗余 activeTab。本轮未修改注入机制。

## 🔧 模块边界

### 1. Service Worker (`background/`)

后台由 `service-worker.js` 顶部的 `importScripts` 装配，职责按文件拆分：

- `service-worker.js`
  - `StateManager`：状态缓存、原子更新、批处理/防抖、性能计数
  - `BackgroundManager`：扩展初始化、runtime 消息路由（switch 分发）、右键菜单注册、标签页更新时的自动启用入口、图标更新协调、错误与反馈收集
- `auto-enable-manager.js`：域名级自动启用（`*.` 通配符匹配、5 分钟域名缓存、标签页防抖、定期清理）
- `icon-manager.js`：图标四态（active/partial/inactive/default）计算、徽章、tooltip 文案（i18n 完整消息模板）
- `monitoring-manager.js`：状态变更日志（1000 条轮转）、平均响应时间、健康检查、日志导出
- `state-confirmation-manager.js`：带 requestId 的状态更新确认（5 秒超时、最多 3 次重试）

`service-worker.js` 是后台的装配与协调点，具体职责由上述独立模块承载。

### 2. Content Script (`content/content.js`)

页面侧的核心逻辑集中在 `CopyPasteManager`：

- 初始化页面状态
- 从 Background 拉取当前插件状态
- 检测页面复制/粘贴限制
- 批量处理 DOM 元素
- 处理复制、粘贴、强力模式等状态切换
- 监听来自 Background 的状态更新
- 维护本地状态队列和失败重试
- SPA 路由感知：`popstate` + MutationObserver 检测 `location.href` 变化，路由切换且插件已启用时重置去重缓存并重放解锁流程

它是“页面行为执行层”，真正负责把插件状态转成页面上的 DOM 行为变化。

### 3. Injector (`content/injector.js`)

`injector.js` 在页面上下文中执行，职责比 `content.js` 更底层：

- 拦截限制性事件监听器（重写 `addEventListener`，正则识别并拒绝注册；吞没名单仅含 selectstart/contextmenu/dragstart/copy/cut/paste 六类纯限制事件，且拦截路径全段容错、不向页面抛异常）
- 运行时中和 `preventDefault` / `stopPropagation` / `stopImmediatePropagation`（中和名单为吞没名单加 mousedown/keydown/keyup；keydown/keyup 仅 ctrl/meta 组合键时中和，mousedown 豁免输入域目标——避免误伤页面快捷键与编辑器；站点级实测依据以 `test/real-sites/` 复测结果为准）
- 清理内联事件限制（含新增节点与属性变更的动态保护）
- 注入强制可选中文本样式
- Shadow DOM 穿透：包装 `Element.prototype.attachShadow`，对每个 shadow root 以 `adoptedStyleSheets` 注入强制可选择样式（`innerHTML` 赋值不会清除该属性）并挂独立观察器；同时覆盖 open 与 closed 模式
- 启停协议：响应 content script 的 `EASYCV_ENABLE` / `EASYCV_DISABLE` postMessage，禁用时恢复全部原型重写、`document.on*` 属性劫持与注入样式

它解决的是 content script 难以直接处理的“页面原生脚本上下文限制”问题。

### 4. Popup (`popup/popup.js`)

Popup 层以 `PopupManager` 为入口，负责：

- 获取当前标签页
- 从 Background 读取完整状态
- 更新弹窗 UI
- 主按钮开关全局复制+粘贴配置，并说明多页面同步范围（独立开关与强力模式收纳在高级选项折叠区；站点规则优先）
- 解锁成功后按设置自动加入自动启用列表（`autoAddToWhitelist`，默认关闭）
- 触发刷新检测、检查复制状态、加入自动启用列表等动作
- 周期性刷新页面状态

2026-11-03 开发态补充（尚未打包）：页面状态读取 `GET_PAGE_STATUS` 响应的 `status.isEnabled/copyEnabled/pasteEnabled`，分别呈现开启、部分开启与关闭；排除列表先于页面查询裁决，浏览器内部页与 Chrome 商店显示不支持，内容脚本无应答时提示刷新并检查访问权限。没有连接的页面禁用检测/检查按钮；非网站地址及排除站点不能从 Popup 加入自动开启。`TEST_COPY` 只返回开关状态，UI 不将 `success` 或 `canCopy` 宣称为真实剪贴板成功，也不把启发式 `restrictions` 当作真实复制验证。

帮助按钮展开 Popup 内的四语言快速指南，无外部导航。反馈按钮打开真实仓库的 GitHub issue 草稿，只预填扩展版本及本地化空白模板；页面 URL、路径、查询参数、浏览器明细及最近失败操作不自动带出，用户自行编辑并提交。状态变更确认后重新查询本页状态，避免一直显示操作前的结果。

页面消息 `GET_PAGE_STATUS/TEST_COPY/REFRESH_DETECTION` 在 MessageUtils 中注册为共享常量，并被 Popup 发送及 Content 接收路由引用。成功率仍没有真实采样写入方；Popup 遇到缺少或无效样本时显示“—”，不将无数据解释为0%。

它是用户最常用的即时控制面板。页面静态文案经 `data-i18n` 属性声明，由 `I18nUtils.applyToPage()` 应用。

### 5. Options (`options/options.js`)

Options 页以 `OptionsManager` 为入口，负责：

- 加载和保存插件设置
- 维护自动启用列表
- 展示统计信息
- 导入/导出设置
- 提供高级设置与数据清理入口

它偏向长期配置，而不是页面级即时操作。

当前实现上，Options 页的大部分设置读写直接通过 `StorageUtils` 访问 `chrome.storage`；只有少量动作会通过消息通知后台或打开外部页面。

### 6. Utils

#### `utils/dom-utils.js`
- 安全地修改样式
- 清理内联事件处理器
- 检测选择限制
- 遍历和筛选可见文本元素

#### `utils/message-utils.js`
- 统一定义消息类型常量
- 封装发往 Background / Content Script 的消息调用
- 提供广播、重试和超时控制

#### `utils/storage-utils.js`
- 封装 `chrome.storage.sync/local`
- 提供插件开关、强力模式、自动启用列表、用户设置、统计数据等读写接口
- 兼容旧数据格式并做本地降级

#### `utils/i18n-utils.js`
- 封装 `chrome.i18n.getMessage`；Chrome 对未匹配语言/缺失消息回退到默认英文包，API 异常时保留调用者兜底
- `applyToPage()` 扫描 `data-i18n` / `data-i18n-placeholder` / `data-i18n-title` / `data-i18n-aria-label` 属性应用文案
- 环境无关：service worker（importScripts）与页面脚本（script 标签）均可使用

#### `utils/notification-utils.js`
- 页面内通知组件（popup 使用；options 使用其页面内自有实现）

## 📡 通信关系

当前系统的主要通信路径如下：

```text
Popup UI ───────────────┐
                        ├── MessageUtils ──> Service Worker
Content Script <────────┘                        │
      │                                          │
      ├── DOMUtils                               ├── StorageUtils
      └── 注入 injector.js 到页面上下文          ├── tabs/contextMenus/runtime
                                                 └── 广播状态到 Content Script

Options Page
      ├── StorageUtils
      ├── 少量 runtime 消息
      └── 配置类页面动作

Injector Script
      └── 处理页面原生脚本层面的限制
```

### 当前消息职责分工

- Popup / Options：
  - Popup 主要经 `MessageUtils` 发起状态变更、查询完整状态、请求页面动作
  - Options 主要直接读写 `StorageUtils`，并在少量场景下通知后台

- Service Worker：
  - 接收并协调状态变更
  - 更新存储
  - 广播状态
  - 处理标签页级逻辑

- Content Script：
  - 响应状态广播
  - 作用于页面 DOM
  - 回传页面分析和错误信息

## 💾 状态与存储

当前状态主要存储在 `chrome.storage.sync`，由 `StorageUtils` 封装访问。

关键存储项包括：

- `plugin_enabled`
- `force_mode`
- `auto_enable_list`
- `user_settings`
- `statistics`
- `interaction_history`

`StateManager` 会在后台维护一份内存缓存，降低高频读取时对存储的直接访问。

## 🧠 当前实现特征

### 模块化后台

后台按职责拆分为 5 个文件，由 `service-worker.js` 顶部的 `importScripts` 装配：

- 优点
  - 状态管理、自动启用、图标、监控、确认机制各自独立，边界清晰
  - 新增后台能力时有明确的落点文件

- 代价
  - `importScripts` 有加载顺序约束（utils 必须先于各 manager）
  - 各 manager 经 `StateManager` 的引用互相协作，排查跨模块流程时需要按调用链追踪

### 双层页面解除限制机制

当前页面侧不是单一路径解除限制，而是两层协作：

1. `content.js` 负责 DOM 层处理和状态应用（含 SPA 路由重放）
2. `injector.js` 负责页面脚本上下文层的拦截和覆盖（含 Shadow DOM 穿透）

这种设计的意义是：既能处理 CSS / DOM 级限制，也能处理页面脚本自己注册的限制性事件逻辑。

### 国际化

- 标准 `_locales` 方案：`en` 为默认回退，支持 `zh_CN`、`ja`、`zh_TW`；跟随浏览器 UI 语言，不增加独立语言选择器或联网翻译
- 静态文案走 `data-i18n` 属性扫描，动态文案走 `I18nUtils.t()`；HTML 初始文案也使用英文
- 每个消息包的 `ui_language` 标记实际译文语言，`applyToPage()` 据此设置 HTML `lang`，四种语言均使用 `dir=ltr`；未支持语言回退英文时不会错误标记为浏览器原始语言
- 四种语言须保持消息键与占位符契约一致，包括帮助、错误、确认、反馈草稿、右键菜单和图标 tooltip；后续功能变更同步维护四份资源
- 图标 tooltip 使用完整消息模板，不做字符串拼接（拼接语序不可翻译）
