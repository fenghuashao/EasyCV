# 文档信息架构与治理（轻量治理）Spec

最后更新：2026-07-28

## Problem Statement

EasyCV 仓库的开发相关文档集中在 `docs/` 目录，但“长期有效的参考/源文档”“阶段性工作文档”“证据文档”“归档材料”“资产文件”混放在同一层级，导致：

- 读者无法快速判断某一领域的 Source Document（当前真相来源）是哪一份，阅读成本高。
- 文档职责边界重叠（例如发布流程、测试执行、过程记录），维护时容易相互漂移。
- 少量内容已与代码现状不一致（如引用了不存在的模块文件、占位仓库地址、未确认的兼容性范围），降低信任度。

结果是：项目在迭代时很难做到“代码与文档同步”，也难以让新贡献者按统一方式更新文档。

## Solution

建立一套“轻量治理”的文档信息架构（IA）与自动验收机制，在不强制大规模迁移文件的前提下：

- 明确每份文档的角色（Source/Reference/Working/Evidence/Governance/Archive/Asset）与“默认入口”。
- 通过一个统一的文档索引入口，让任何人能在 30 秒内定位应该读/应该改的那份文档。
- 引入单一验收缝（seam）：`docs:check` 脚本，自动检查索引完整性、占位内容、过时引用（指向不存在文件/不匹配现状的声明），将文档漂移从“主观”变成“可被自动发现”。
- 使用项目词汇表（`CONTEXT.md`）固化分类术语，避免后续讨论中概念漂移。

## User Stories

1. 作为维护者，我想要一个统一的文档入口索引，这样我能快速判断“现在应该看哪份文档”。
2. 作为维护者，我想要在索引里明确每份文档的角色（Source/Reference/Working/Evidence/Governance/Archive/Asset），这样团队能用同一套语言讨论“这份文档应该怎么维护”。
3. 作为维护者，我想要标记每份文档是否为当前有效（active）或归档（archive），这样新同学不会误读历史材料。
4. 作为贡献者，我想要知道当我改动某个模块/功能时需要同步更新哪些 Source Document，这样我不会漏掉文档更新。
5. 作为贡献者，我想要知道当我只做了一次测试/验证时应该往哪里写 Evidence Document，这样历史证据可以被追溯。
6. 作为测试人员，我想要明确测试策略、用例库、执行指南三者的边界，这样测试文档不会互相复制粘贴。
7. 作为发布负责人，我想要发布流程文档与构建脚本文档职责清晰，这样修改发布流程时不会漏改关键步骤。
8. 作为维护者，我想要自动检测文档里是否存在占位内容（例如占位仓库地址），这样文档可以用于真实交付。
9. 作为维护者，我想要自动检测文档里是否引用了不存在的文件/模块，这样可以及时修复“与代码不一致”的陈述。
10. 作为维护者，我想要自动检测文档与当前 manifest/脚本的关键声明是否矛盾（例如浏览器支持范围、脚本名称），这样避免发布前踩坑。
11. 作为 AI 开发助手，我想要有一份治理规则可引用，这样我能在每次改动后按规则更新文档。
12. 作为维护者，我想要把资产（svg、生成器等）与文档正文区分开，这样 docs 目录更易浏览。
13. 作为维护者，我想要在索引中列出“默认真相来源”和“相关辅助材料”，这样信息不丢但也不混。
14. 作为贡献者，我想要在索引中看到每份文档的更新时间/维护频率约定，这样我知道哪些需要经常维护。
15. 作为维护者，我想要把阶段性记录（开发日志、阶段测试报告）明确为 Archive 或 Evidence，这样不会反向污染当前设计。
16. 作为维护者，我想要在文档中用一致的术语描述同一件事（例如 Source Document、Evidence Document），这样沟通成本更低。
17. 作为维护者，我想要在 CI 或本地一键运行 `docs:check`，这样任何人都能在提交前发现文档问题。
18. 作为维护者，我想要 `docs:check` 在失败时给出可执行的修复建议（指向哪个文档、哪段内容），这样修复成本可控。
19. 作为维护者，我想要在未来选择“是否迁移目录结构”时有明确的增量路径，这样不会一次性大改导致历史 PR 难追。
20. 作为用户文档维护者，我想要把“已发布/未发布”的安装方式表达清楚，这样不会对外造成误导。
21. 作为维护者，我想要对“是否支持 Firefox”等声明有统一决策位置，这样不会在多个文档里出现矛盾。
22. 作为维护者，我想要让文档维护成为可自动验收的一部分，这样文档不会只靠自觉。
23. 作为新贡献者，我想要从索引快速理解项目模块（background/content/popup/options/utils/scripts），这样我能更快上手。
24. 作为维护者，我想要在索引中记录“哪些文档是必须保持与代码同步”的，这样同步成本有重点。
25. 作为维护者，我想要将“项目过程/任务清单”与“产品需求”分离，这样需求不会被过程信息淹没。
26. 作为维护者，我想要明确每份文档的推荐读者（开发/测试/发布/用户），这样不同角色能快速定位。
27. 作为维护者，我想要在文档治理中保留研究报告的价值但不让其混入当前实现说明，这样既能溯源又能保持清晰。
28. 作为维护者，我想要让 `docs:check` 能在未来扩展规则但保持单一入口，这样验收方式长期稳定。

## Implementation Decisions

- 采用“轻量治理”路线：不要求立即迁移现有文件，仅新增并维护一个权威索引入口，逐步收敛职责边界。
- 使用 `CONTEXT.md` 作为文档治理术语的唯一真相来源，术语至少包含：Source Document、Reference Document、Working Document、Evidence Document、Governance Document、Archive、Asset。
- 新增一个文档索引入口（例如 `docs/README.md`），包含：
  - 文档分类（按角色与主题）
  - 每份文档的角色与状态（active/archive）
  - 每个主题的“默认真相来源”（Source Document）
  - 维护触发条件（何时必须更新）
- 在不改变核心开发体验的前提下，引入唯一验收缝：`docs:check`（npm script），其规则至少覆盖：
  - 索引中列出的文件必须存在
  - 文档中出现的明显占位内容必须被替换或显式标记为“未来态”
  - 文档中引用的仓库内文件路径必须存在（避免指向不存在模块）
  - 与项目关键配置的陈述不得自相矛盾（例如脚本名称、支持浏览器范围等）
- 对已发现的高价值漂移点进行一次性修复，使“当前默认入口文档”恢复可信：
  - 架构文档中不应引用不存在的模块文件
  - 部署/发布文档中不应引用不存在的脚本或占位仓库地址
  - 测试文档中对兼容性范围的声明应与当前目标一致
- 如果需要记录“文档 IA 结构/验收方式”的不可逆决策，可新增一条 ADR（仅当该决策满足难以逆转、没有上下文会惊讶、存在真实权衡）。

## Testing Decisions

- 好的测试只验证外部行为：
  - `docs:check` 返回 0 表示通过；返回非 0 表示失败并输出可定位的问题列表。
  - 不测试脚本内部实现细节（例如具体正则），只测试输入输出与失败信息是否覆盖关键场景。
- 单一测试缝：以 `npm run docs:check` 作为唯一验收入口。
- 覆盖场景（最小集合）：
  - 索引引用不存在文件时失败
  - 文档包含占位字符串（如占位仓库地址）时失败
  - 文档引用不存在仓库路径时失败
  - 与 manifest/脚本声明冲突时失败
- Prior art：仓库已存在 `scripts/` 目录与 node 脚本运行方式，`docs:check` 复用同一模式。

## Out of Scope

- 一次性大规模迁移/重命名所有 docs 文件（允许作为后续迭代）。
- 将 `.txt` 全量转换为 `.md` 或重写内容结构（允许后续逐步演进）。
- 为文档治理引入复杂的静态站点生成、全文搜索、外部发布流水线。
- 自动“修复”文档内容（本期以检测和提示为主）。

## Further Notes

- 现状中已存在《文档维护指南》《AI开发助手指南》等 Governance Document，但它们与“单一权威索引入口 + 自动验收”之间缺少强绑定；本工作将补足这一缺口。
- 本 spec 以“让文档再次可信”为第一优先级：先解决漂移与入口不清，再考虑更激进的目录重构。
