# EasyCV 技术架构文档

## 🏗️ 整体架构

EasyCV 当前采用 Chrome Extension Manifest V3 架构，核心由 `background`、`content`、`popup`、`options` 和 `utils` 五组模块组成。

当前仓库中的真实结构如下：

```text
EasyCV/
├── manifest.json
├── background/
│   └── service-worker.js
├── content/
│   ├── content.js
│   └── injector.js
├── popup/
│   ├── popup.html
│   ├── popup.js
│   └── popup.css
├── options/
│   ├── options.html
│   ├── options.js
│   └── options.css
├── utils/
│   ├── dom-utils.js
│   ├── message-utils.js
│   └── storage-utils.js
└── icons/
    ├── icon-default-*.png
    └── icon-active-*.png
```

> 说明：本文档只描述当前仓库中真实存在的文件和由这些文件承载的职责边界，不再把未落地的拆分文件当作现状模块。

## 🔧 模块边界

### 1. Service Worker (`background/service-worker.js`)

当前后台能力集中在一个文件中实现，主要包含两个核心类：

- `StateManager`
  - 负责插件状态缓存
  - 负责把状态写入 `chrome.storage`
  - 负责状态更新队列、批处理和简单性能统计
  - 负责对外提供完整状态读取接口

- `BackgroundManager`
  - 负责扩展初始化
  - 负责 runtime 消息路由
  - 负责右键菜单注册
  - 负责标签页更新时的自动启用入口
  - 负责图标更新和状态广播

当前这个文件同时承载了：
- 状态管理
- 自动启用流程入口
- 图标更新协调
- 错误与反馈收集
- 基础性能/监控数据输出

换句话说，`service-worker.js` 现在是后台的集中式协调点，而不是多个独立后台文件拼装后的外壳。

### 2. Content Script (`content/content.js`)

页面侧的核心逻辑集中在 `CopyPasteManager`：

- 初始化页面状态
- 从 Background 拉取当前插件状态
- 检测页面复制/粘贴限制
- 批量处理 DOM 元素
- 处理复制、粘贴、强力模式等状态切换
- 监听来自 Background 的状态更新
- 维护本地状态队列和失败重试

它是“页面行为执行层”，真正负责把插件状态转成页面上的 DOM 行为变化。

### 3. Injector (`content/injector.js`)

`injector.js` 在页面上下文中执行，职责比 `content.js` 更底层：

- 拦截限制性事件监听器
- 覆盖 `preventDefault` / `stopPropagation` 的限制路径
- 清理内联事件限制
- 注入强制可选中文本样式
- 监听动态 DOM 变化并持续移除限制

它解决的是 content script 难以直接处理的“页面原生脚本上下文限制”问题。

### 4. Popup (`popup/popup.js`)

Popup 层以 `PopupManager` 为入口，负责：

- 获取当前标签页
- 从 Background 读取完整状态
- 更新弹窗 UI
- 响应复制/粘贴/强力模式切换
- 触发刷新检测、测试复制、加入自动启用列表等动作
- 周期性刷新页面状态

它是用户最常用的即时控制面板。

### 5. Options (`options/options.js`)

Options 页以 `OptionsManager` 为入口，负责：

- 加载和保存插件设置
- 维护自动启用列表
- 展示统计信息
- 导入/导出设置
- 提供高级设置与数据清理入口

它偏向长期配置，而不是页面级即时操作。

当前实现上，Options 页的大部分设置读写直接通过 `StorageUtils` 访问 `chrome.storage`；只有少量动作会通过消息通知后台或打开外部页面。

### 6. Utils

#### `utils/dom-utils.js`
- 安全地修改样式
- 清理内联事件处理器
- 检测选择限制
- 遍历和筛选可见文本元素

#### `utils/message-utils.js`
- 统一定义消息类型常量
- 封装发往 Background / Content Script 的消息调用
- 提供广播、重试和超时控制

#### `utils/storage-utils.js`
- 封装 `chrome.storage.sync/local`
- 提供插件开关、强力模式、自动启用列表、用户设置、统计数据等读写接口
- 兼容旧数据格式并做本地降级

## 📡 通信关系

当前系统的主要通信路径如下：

```text
Popup UI ───────────────┐
                        ├── MessageUtils ──> Service Worker
Content Script <────────┘                        │
      │                                          │
      ├── DOMUtils                               ├── StorageUtils
      └── 注入 injector.js 到页面上下文          ├── tabs/contextMenus/runtime
                                                 └── 广播状态到 Content Script

Options Page
      ├── StorageUtils
      ├── 少量 runtime 消息
      └── 配置类页面动作

Injector Script
      └── 处理页面原生脚本层面的限制
```

### 当前消息职责分工

- Popup / Options：
  - Popup 主要经 `MessageUtils` 发起状态变更、查询完整状态、请求页面动作
  - Options 主要直接读写 `StorageUtils`，并在少量场景下通知后台

- Service Worker：
  - 接收并协调状态变更
  - 更新存储
  - 广播状态
  - 处理标签页级逻辑

- Content Script：
  - 响应状态广播
  - 作用于页面 DOM
  - 回传页面分析和错误信息

## 💾 状态与存储

当前状态主要存储在 `chrome.storage.sync`，由 `StorageUtils` 封装访问。

关键存储项包括：

- `plugin_enabled`
- `force_mode`
- `auto_enable_list`
- `user_settings`
- `statistics`
- `interaction_history`

`StateManager` 会在后台维护一份内存缓存，降低高频读取时对存储的直接访问。

## 🧠 当前实现特征

### 集中式后台

当前后台不是“每种职责一个独立文件”的拆分架构，而是把后台主流程集中在 `service-worker.js` 中。  
这带来的直接特点是：

- 优点
  - 当前入口清晰，排查主流程时只需要先看一个文件
  - 状态管理、消息路由和初始化路径集中，便于追踪

- 代价
  - 后台文件体积较大
  - 多种职责耦合在一个模块里
  - 后续继续扩展时，维护成本会逐步上升

### 双层页面解除限制机制

当前页面侧不是单一路径解除限制，而是两层协作：

1. `content.js` 负责 DOM 层处理和状态应用
2. `injector.js` 负责页面脚本上下文层的拦截和覆盖

这种设计的意义是：既能处理 CSS / DOM 级限制，也能处理页面脚本自己注册的限制性事件逻辑。

## ⚠️ 当前代码现状说明

为了让文档和仓库真实状态保持一致，这里记录两个重要事实：

1. 当前后台职责主要集中在 `service-worker.js` 中，而不是已经完全拆成多个独立后台模块。
2. `service-worker.js` 顶部仍保留了若干指向不存在文件的 `importScripts` 导入语句，这说明当前代码本身仍存在后台模块拆分未完成的遗留不一致。

这也是本文档本次修订的核心原则：**文档只描述当前存在且可追踪的实现边界，同时把仍然存在的代码级不一致明确标出来，而不是把它们写成已经完成的现状模块。**

## 🧪 测试关注点

从当前架构看，最值得测试的边界是：

1. Background 状态读写与广播
2. Content Script 状态应用与 DOM 处理
3. Popup / Options 与 Background 的消息交互
4. Injector 对页面限制逻辑的干预是否生效
